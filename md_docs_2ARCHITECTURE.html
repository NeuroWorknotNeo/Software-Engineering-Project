1. Общая схема

Приложение — конвейер обработки данных. Каждый шаг — отдельный модуль библиотеки quant, консольная утилита только разбирает параметры и соединяет шаги.

flowchart LR
MOEX[(MOEX ISS)] -->|scripts/download_prices.py| CSV[data/prices.csv]
CSV --> D[data<br/>чтение, выравнивание,<br/>сплиты, проверки]
D --> S[stats<br/>доходности, μ, Σ]
S --> O[optim<br/>GMV, max Sharpe,<br/>граница]
S --> B[backtest<br/>скользящее окно,<br/>ребалансировка]
O --> B
O --> W[io<br/>CSV-результаты]
B --> W
W --> P[scripts/plot_*.py<br/>графики для отчёта]

Правило зависимостей: data → stats → optim → backtest. Математические модули (stats, optim) не знают о файлах и консоли — их можно тестировать на синтетических данных. Чтение и запись файлов — только в data и io.

5. Архитектурные решения

ADR-1. Метод оптимизации без коротких продаж (FR-12…FR-14)

Все три задачи сводятся к одной задаче квадратичного программирования:

min ½·xᵀQx + cᵀx при Ax = b, x ≥ 0

(для максимального Шарпа: min yᵀΣy при (μ − r_f·1)ᵀy = 1, y ≥ 0, затем w = y / (1ᵀy); требует, чтобы хотя бы у одного актива μᵢ > r_f).

Вариант Плюсы Минусы
(а) Метод активного множества (свой) Точное решение за конечное число шагов; быстро для n ≤ 100; без зависимостей Сложнее реализовать, нужна аккуратность с вырожденными случаями
(б) Проекционный градиентный спуск (свой) Очень простой код Итерационный, медленно сходится при плохой обусловленности Σ, нужно подбирать шаг и точность
(в) Готовый решатель OSQP Надёжный, проверенный Внешняя C-библиотека, усложняет сборку; приближённое решение (ADMM)

Решение: (а) — основной решатель; (б) — эталон для тестов и сравнение в бенчмарке; (в) — не используем.

Обоснование: (а) даёт точность из NFR-2 и скорость из NFR-1 без новых зависимостей. (б) настолько прост, что почти не может содержать ошибок, поэтому годится для перекрёстной проверки, а сравнение скорости (а) и (б) войдёт в отчёт. Риск сложности (а) закрывается тем, что (б) уже будет работать.

Реализация и результаты (27.11.2026):

  • (б) реализован только для симплекса {x ≥ 0, 1ᵀx = b}: проекция на него вычисляется за O(N log N). Поэтому (б) решает задачу GMV и задачу min ½wᵀΣw − τ·μᵀw, а точки границы с ограничением μᵀw = r и касательный портфель решает только (а).
  • Тесты сверяют (а) и (б) на 20 случайных моделях (расхождение ≤ 1e-7), (а) — с аналитическим решением, когда ограничение неактивно (≤ 1e-8), и с условиями ККТ. На реальных данных результаты (а) совпали со scipy (SLSQP) до 1e-8.
  • Бенчмарк GMV без коротких продаж: 20 бумаг — (а) 19 мкс, (б) 62 мкс; 50 бумаг — (а) 0,26 мс, (б) 0,53 мс; 100 бумаг — (а) 5,6 мс, (б) 3,1 мс. Число итераций (а) растёт с числом бумаг, а каждая итерация решает систему ККТ, поэтому на больших N (б) быстрее, но даёт только приближённое решение.
  • NFR-1: граница из 50 точек без коротких продаж для 50 бумаг × 1000 дней вместе с оценкой Ledoit–Wolf — около 24 мс (требование — ≤ 1 с).

ADR-2. Линейная алгебра

Варианты: Eigen 3 / собственные матрицы / BLAS+LAPACK. Решение: Eigen 3 — стандарт в индустрии, только заголовки, есть разложения Холецкого и LDLᵀ для решения систем. Подключается через find_package, при отсутствии — через FetchContent.

ADR-3. Хранение данных

Варианты: CSV-файлы / SQLite. Решение: CSV в широком формате (date,TICKER1,...). Объём маленький (~1700 дней × 20 бумаг), файлы удобно смотреть глазами и класть в репозиторий для воспроизводимости (NFR-3). Сплиты — отдельный splits.csv (date,ticker,ratio).

ADR-4. Аналитическое решение с короткими продажами (FR-9…FR-11)

Решается через множители Лагранжа: GMV — w = Σ⁻¹1 / (1ᵀΣ⁻¹1), касательный портфель — w ∝ Σ⁻¹(μ − r_f·1), граница — линейная комбинация двух портфелей. Системы решаются разложением LDLᵀ без явного обращения Σ (устойчивее численно). Если Σ вырождена — ошибка с предложением использовать Ledoit–Wolf.

ADR-5. Параллельность бэктеста (C)

Целевые веса на разных датах ребалансировки зависят только от окна данных и не зависят друг от друга. Поэтому RunBacktest сначала считает веса на всех датах, разбивая даты на блоки по числу ядер (std::thread::hardware_concurrency) и запуская блоки через std::async, а затем последовательно прогоняет стоимость портфеля по дням (этот шаг зависит от предыдущего дня). Общего изменяемого состояния у потоков нет: стратегии, оптимизаторы, решатели и оценщики ковариации — объекты без изменяемых полей, поэтому мьютексы не нужны, а результат совпадает с последовательным побитово (тест Backtester.ParallelMatchesSequential).

Бенчмарк (bench/bench_backtest.cpp, 2016 дней, окно 252, max-Sharpe без коротких продаж, Ledoit–Wolf, 4 ядра): 20 бумаг — 8,3 мс последовательно и 4,2 мс параллельно (×2,0); 50 бумаг — 56 мс и 16 мс (×3,5). Чем дороже одна оптимизация, тем ближе ускорение к числу ядер.

ADR-7. Если портфеля максимального Шарпа не существует (FR-17)

На отдельных датах бэктеста касательный портфель может не существовать: с короткими продажами — если доходность GMV в окне не выше безрисковой ставки, без коротких продаж — если ни одна бумага не обгоняет ставку. Варианты: (а) оставить прежние веса, (б) уйти в равновзвешенный портфель, (в) взять портфель минимальной дисперсии того же режима. Решение: (в) — самый консервативный выбор, согласованный с логикой стратегии (минимум риска, когда за риск не платят). Такие даты помечаются (Rebalance::is_fallback) и считаются в метриках (PerformanceMetrics::fallback_count).

ADR-6. Обработка ошибок

Библиотека бросает исключения (std::invalid_argument, std::runtime_error с понятным текстом). main перехватывает их, печатает сообщение в stderr и возвращает код 1 (некорректный ввод) или 2 (ошибка расчёта).
